# Burndown Tracker — трекер сгорания работ

Веб-приложение для отслеживания сгорания задач по эпикам и этапам проектов. Поддерживает мультипроектность, ролевую модель и авторизацию.

## Возможности

- Многопроектная структура (каждый проект — отдельные эпики, этапы, замеры)
- «Выводы» о сроках на уровне эпика, этапа, проекта и портфеля: главное, нужный темп, тренд темпа, рост объёма,
  сдвиг прогноза, свежесть данных; портфель проектов; выводы в дайджесте и PDF
- Лента изменений выводов по неделям: «что изменилось за неделю» в выводах и дайджесте (ежедневные снимки)
- Настройки проекта: рабочие дни с праздниками, часы или человеко-дни, уровень доверия прогноза, пороги выводов;
  личный вид дашборда и свода
- Графики сгорания с прогнозом, средней динамикой и целевыми линиями
- Расширенные тултипы: отклонения факта от средней динамики и прогноза
- Свод по этапам (группировка эпиков по этапу или явной группе), признак «сдано» и быстрые фильтры
- Ввод замера на одну дату сразу по всем эпикам; рост оценки (Δ оценки) и подсветка роста остатка
- Выгрузка в PDF (таблицы) и печать разделов с графиками; экспорт проекта в JSON
- Реестр изменений с фильтрами
- Мастер подключения проекта к Jira: эпики из структуры или JQL, кнопка среза, замер на сегодня, история и автозаполнение за один проход
- Эпики, целевые даты и признак «Сдано» из Jira — с предпросмотром и автоматически перед автозаполнением
- Связь с Jira: кнопки «срез из Structure» заполняют замеры остатком, затраченным временем и оценкой — суммой полей Jira или значением колонки Structure через Value API Structure;
  колонка задаётся как в Structure: поле или формула (любые поля, включая статус), Σ по вложенным, исключение дубликатов,
  «После фильтрации» — с тем же фильтром доски (JQL или трансформации Structure)
- Автозаполнение замеров из Jira по расписанию и по событиям Jira (вебхук)
- Запись прогноза, статуса сроков и шанса успеть в поля задач Jira; еженедельный отчёт проекта в Confluence
- Состав эпиков по задачам Jira: статусы, burn-up, разбор изменений объёма и проверка качества данных
- Восстановление истории замеров по журналу изменений Jira
- Прогноз диапазоном: шанс успеть к цели и диапазон 50–90% (Монте-Карло), дрейф прогноза
- Прогноз по burn-up; задачи Jira по этапам и по проекту
- Уведомления на почту и в Telegram: дайджест по проекту по расписанию (с PDF) и оповещения об ухудшении сроков и данных;
  команды Telegram-бота /status, /risks, /week, /projects
- Интеграции (Jira, Confluence, почта, Telegram) настраивает администратор централизованно для всех проектов
- Быстрая работа под нагрузкой: кэш расчётов по версии данных и общий кэш Монте-Карло в базе, ETag/304, gzip,
  режим WAL, фоновый пересчёт выводов
- Общий производственный календарь (праздники РФ 2025–2027 внесены), «Состояние системы» и оповещения администратору о сбоях
- «О программе», история версий (из `docs/versions.md`) и руководство пользователя — открыть в браузере или скачать (PDF, DOCX)
- Ролевая модель: администратор, руководитель проекта, пользователь
- Авторизация по логину/паролю
- Хранение данных в SQLite

## Технологии

- Python 3.10+ / Flask
- SQLite (встроена в Python)
- Chart.js и шрифты — локальные копии в `static/vendor` (работает без доступа в интернет)
- Gunicorn (продакшен)

## Развёртывание на Ubuntu 24.04

### 1. Установка системных пакетов

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip nginx
```

### 2. Создание пользователя и директории

```bash
sudo useradd -m -s /bin/bash burndown
sudo mkdir -p /opt/burndown
sudo chown burndown:burndown /opt/burndown
```

### 3. Копирование файлов

Скопируйте все файлы приложения в `/opt/burndown`:

```bash
sudo -u burndown cp -r /path/to/burndown-app/* /opt/burndown/
```

### 4. Создание виртуального окружения и установка зависимостей

```bash
sudo -u burndown bash -c '
cd /opt/burndown
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
'
```

### 5. Инициализация базы данных

```bash
sudo -u burndown bash -c '
cd /opt/burndown
source venv/bin/activate
python init_db.py
'
```

База данных `burndown.db` будет создана в директории приложения.

Будет создан пользователь по умолчанию:
- Логин: `admin`
- Пароль: `Test198!`

Созданы проекты:
- **АИСУЗ** — с предзаполненными данными
- **ИСУП** — пустой проект

### 6. Настройка Gunicorn через systemd

Создайте файл `/etc/systemd/system/burndown.service`:

```ini
[Unit]
Description=Burndown Tracker (Gunicorn)
After=network.target

[Service]
User=burndown
Group=burndown
WorkingDirectory=/opt/burndown
Environment="PATH=/opt/burndown/venv/bin"
Environment="DB_PATH=/opt/burndown/burndown.db"
ExecStart=/opt/burndown/venv/bin/gunicorn -w 4 -k gthread --threads 8 --timeout 120 -b 127.0.0.1:5000 app:app
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

> **Секретный ключ сессий.** Если `SECRET_KEY` не задан, при первом запуске генерируется случайный ключ
> и сохраняется в файл `.secret_key` рядом с базой данных (права 600) — обычно этого достаточно. Чтобы задать
> ключ явно, сгенерируйте его (`openssl rand -hex 32`) и добавьте `Environment="SECRET_KEY=<ключ>"`. Ключ
> короче 32 символов не используется: вместо него берётся `.secret_key`, а токены, зашифрованные коротким
> ключом, автоматически перешифровываются. При работе через HTTPS добавьте `Environment="SESSION_COOKIE_SECURE=1"` —
> cookie сессии будет передаваться только по защищённому соединению.
>
> **Пароль администратора.** `init_db.py` создаёт `admin` / `Test198!`. Пока пароль не сменён, в меню
> показывается предупреждение — смените его в профиле сразу после установки.

Запуск:

```bash
sudo systemctl daemon-reload
sudo systemctl enable burndown
sudo systemctl start burndown
sudo systemctl status burndown
```

### 7. Настройка Nginx (обратный прокси)

Создайте файл `/etc/nginx/sites-available/burndown`:

```nginx
server {
    listen 80;
    server_name ваш-домен-или-ip;

    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /static/ {
        alias /opt/burndown/static/;
        expires 30d;
        gzip on;
        gzip_types text/css application/javascript image/svg+xml;
    }
}
```

Ответы API Burndown сжимает сам (gzip) и помечает ETag — дополнительных настроек nginx для них не нужно. Адреса
стилей и скрипта содержат метку версии (`?v=…`), поэтому кэш статики на 30 дней не мешает обновлениям.

Активация:

```bash
sudo ln -s /etc/nginx/sites-available/burndown /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl restart nginx
```

### 8. Настройка HTTPS (рекомендуется)

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ваш-домен-или-ip
```

## Управление

### Перезапуск приложения

```bash
sudo systemctl restart burndown
```

### Просмотр логов

```bash
sudo journalctl -u burndown -f
```

### Резервное копирование базы данных

База работает в режиме WAL (рядом с `burndown.db` — файлы `burndown.db-wal` и `burndown.db-shm`), поэтому копию
работающей базы делайте командой `.backup` (пакет `sqlite3`), а не `cp`:

```bash
sudo -u burndown sqlite3 /opt/burndown/burndown.db ".backup /opt/burndown/backup/burndown-$(date +%Y%m%d).db"
```

Восстановление: остановите службу, удалите `burndown.db-wal` и `burndown.db-shm`, замените `burndown.db` копией,
запустите службу.

### Сброс базы данных

```bash
sudo -u burndown bash -c '
cd /opt/burndown
source venv/bin/activate
python init_db.py
'
sudo systemctl restart burndown
```

## Связь с Jira (срез из Structure)

Интеграции настраиваются централизованно: **подключение к Jira одно для всех проектов**, его задаёт только
администратор в разделе **«Интеграции»**. Руководитель проекта в разделе **«Jira и Confluence»** своего проекта видит
только факт подключения (настроено или нет; адрес, учётная запись и подробности ошибок — только администратору)
и настраивает связки: кнопки среза, поля, расписание автозаполнения, восстановление истории.

1. **Подключение** («Интеграции», администратор) — устроено как в jira_mass_logger:
   - Jira Server/DC — логин и пароль (Basic, UTF-8), REST API v2 — по умолчанию;
   - Jira Server/DC — Personal Access Token (Bearer), REST API v2;
   - Jira Cloud — email + API-токен, REST API v3;
   - опция «Не проверять TLS-сертификат» для самоподписанных/корпоративных сертификатов;
   - понятное сообщение, если Jira после неудачных входов требует CAPTCHA (`X-Authentication-Denied-Reason`).

   Пароль или токен хранится в БД зашифрованным (ключ — производный от `SECRET_KEY`) и никогда не возвращается
   в интерфейс. Прокси для запросов в Jira берётся из окружения сервера (`HTTPS_PROXY`, `NO_PROXY`). При обновлении
   с версий до 1.6.0 общим становится подключение проекта, где больше всего кнопок среза.
2. **Кнопки среза** — у кнопки задаются название, структура Structure (список подгружается из Jira, либо ID вручную)
   и ассоциации «эпик ← задачи Jira» с флажком «С вложенными».
3. **Поля Jira** — у кнопки выбирается, из каких полей брать остаток, затраченное время и оценку: по умолчанию
   стандартный учёт времени (`timeestimate`, `timespent`, `timeoriginalestimate`, в секундах), либо любые числовые
   поля, в том числе пользовательские (в часах или секундах); показатель можно не заполнять.
4. **Срез** — кнопка появляется в разделе «Данные по датам». По нажатию для каждого эпика суммируются выбранные поля:
   - со структурой и «С вложенными» — все задачи поддерева указанных задач в структуре (каждая один раз);
   - без структуры и «С вложенными» — задача вместе с подзадачами (поиск `parent in (...)`);
   - без «С вложенными» — только сами указанные задачи.

   Значения показываются в окне замера: их можно проверить и поправить перед сохранением.
5. **Автозаполнение** — после первого успешного среза по кнопке в разделе «Автозаполнение» включается расписание:
   дни недели, время, часовой пояс, перезапись уже внесённого замера. Сервер сам забирает срез и сохраняет замер
   на текущую дату; результат виден в карточке кнопки и в реестре изменений (автор «Автозаполнение»).
6. **Задачи Jira на дашборде** — каждый срез сохраняет состав эпиков по задачам на день среза
   (таблица `jira_issue_snapshots`). На дашборде: «Задачи Jira по эпикам» (статусы задач, доля выполненного объёма,
   проблемы данных), burn-up выбранного эпика (объём и выполнено по датам срезов) и список задач со ссылками в Jira
   и фильтром проблем: не закрыта без оценки, закрыта с остатком, в работе с нулевым остатком, перерасход.
   Таблица состава попадает и в PDF-отчёт дашборда.
7. **Что изменилось** — разбор изменения объёма эпика между двумя срезами: новые, убранные и переоценённые задачи
   (каскадная диаграмма и списки), закрытые и переоткрытые за период; в списке задач — изменения с прошлого среза.
8. **Восстановление истории** — замеры и состав задач на прошлые даты по журналу изменений Jira (фоновая задача
   с прогрессом, таблица `jira_history_jobs`); ручные замеры по умолчанию не изменяются.

**Прогноз диапазоном.** Для эпиков и этапов считается «шанс успеть» к цели и диапазон 70% (P15–P85) методом
Монте-Карло по интервалам между замерами; диапазон рисуется на графике эпика.

**Дрейф прогноза.** На дашборде — как менялась прогнозная дата эпика от замера к замеру (прогноз «0», медиана
и диапазон 70%, цель) и насколько она сдвинулась с прошлого и с первого прогноза.

**Прогноз по burn-up и уровень этапа и проекта.** Дата, когда «Выполнено» догонит «Объём» при текущих темпах
выполнения и роста объёма (регрессия по срезам задач) — на burn-up и в таблицах задач Jira; в своде по этапам —
задачи Jira по этапам с итогом по проекту и burn-up этапа или всего проекта. Те же данные — в PDF дашборда и свода.

Для кнопок со структурой нужен плагин Structure (Tempo, ранее ALM Works) с REST API `/rest/structure/2.0`
(Jira Server/DC). Работа с Structure в Jira Cloud не проверялась: если API недоступен, приложение сообщит об этом —
в таком случае используйте кнопки без структуры.

**Планировщик автозаполнения** — фоновый поток в процессе приложения (проверка раз в 30 секунд), отдельная служба
или cron не нужны. Каждая кнопка запускается не чаще раза в день: день запуска захватывается в БД атомарно, поэтому
несколько воркеров gunicorn не дублируют срез; если сервер был остановлен во время запуска, срез выполнится позже
в тот же день. Отключить планировщик в процессе — `BURNDOWN_SCHEDULER=0`.

**По событиям Jira (вебхук).** Администратор в «Интеграциях» включает вебхук и получает адрес
`<адрес Burndown>/api/jira/webhook/<секрет>` для веб-хука Jira (события задач). Кнопки с отметкой «по событиям Jira»,
к которым относится изменённая задача, выполняют срез на сегодня через 2 минуты (серия правок — один срез, повторно —
не чаще раза в 10 минут).

**Прогноз в Jira.** С разрешения администратора проект записывает в пользовательские поля задач эпиков прогноз
завершения, статус сроков, шанс успеть и главный вывод — только изменившиеся значения, автоматически после изменения
данных (не чаще раза в 10 минут) и вручную. Нужны поля на экране редактирования и право учётной записи подключения
редактировать задачи.

## Отчёт в Confluence

Администратор задаёт общее подключение к Confluence (Server/DC — PAT или логин и пароль, Cloud — email и API-токен;
`CONFLUENCE_ALLOWED_HOSTS` ограничивает хосты). Проект публикует отчёт — статус, ключевые цифры, риски, изменения
за неделю, этапы и эпики — раз в неделю по расписанию или вручную: одна обновляемая страница или новая страница
каждую неделю, в заданном пространстве и под родительской страницей.

## Уведомления: почта и Telegram

Администратор в разделе **«Интеграции»** настраивает SMTP-сервер (STARTTLS, SSL/TLS или без шифрования), токен
Telegram-бота (создаётся у @BotFather) и внешний адрес Burndown для ссылок в сообщениях. Пароль SMTP и токен бота
хранятся зашифрованными (ключ — `SECRET_KEY`) и в интерфейс не возвращаются; все отправки видны в журнале.

Пользователь в разделе **«Уведомления»** проекта выбирает каналы (почта из профиля и/или Telegram — привязка
по ссылке `t.me/<бот>?start=<код>`), включает:

- **дайджест** — по дням недели, времени и часовому поясу: статусы эпиков, остаток, прогноз, шанс успеть
  и изменения с прошлого дайджеста, по желанию — PDF дашборда;
- **оповещения** — при ухудшении статуса эпика или этапа, падении шанса успеть ниже порога, росте объёма задач
  Jira за срез, росте числа задач с неполными данными и ошибке автозаполнения.

Цифры в сообщениях считает сервер (`forecast.py`) по тем же правилам, что и интерфейс, включая Монте-Карло, — они
совпадают с дашбордом. Дайджесты и оповещения отправляет тот же планировщик, что и автозаполнение; дайджест
отправляется один раз в день на подписку, оповещения проверяются при изменениях в проекте (реестр, срезы Jira).
Серверу нужен доступ к SMTP-серверу и к `api.telegram.org:443` (прокси — `HTTPS_PROXY`); для Telegram входящие
соединения не нужны (длинный опрос).

**Команды бота.** Привязанные пользователи спрашивают бота: `/status` — статус и главное, `/risks` — главные риски,
`/week` — что изменилось за неделю, `/projects` — список проектов (по-русски тоже: `/статус`, `/риски`, `/неделя`);
проект — номером из списка или частью названия. Сообщения бота получает один процесс (файловая блокировка рядом
с базой); выключается в «Интеграциях».

## Производительность

- Монте-Карло ускорен: длинные ряды замеров объединяются в недельные интервалы, расчёт останавливается, когда цель
  уже недостижима; результаты хранятся в базе (`mc_cache`) и общие для воркеров.
- «Выводы», сводки и состав задач кэшируются по версии данных проекта (замеры, эпики, цели, настройки, срезы Jira,
  календарь, дата); «Выводы» — ещё и в базе (`result_cache`); после изменения данных пересчитываются в фоне
  (`BURNDOWN_WARMUP=0` — выключить).
- Тяжёлые ответы (`/data`, `/insights`, `/jira/composition`) отдаются с ETag: повтор без изменений — 304 без тела;
  ответы больше 1,4 КБ сжимаются gzip.
- SQLite в режиме WAL с ожиданием блокировки до 10 с; индексы для отпечатка версии и вебхуков.
- Интерфейс: плотные графики без анимации и маркеров точек, дрейф прогноза — не больше 90 дат, кэш разбора дат.

На стенде (4 ядра, `-w 4 -k gthread --threads 8`, проект из 40 эпиков и 10 400 замеров, 50 пользователей без пауз):
около 450 запросов в секунду только на чтение и 125–165 — при непрерывной записи замеров, без ошибок; тёплые
ответы — 4–13 мс.


## Руководства

Готовые руководства пользователя и администратора (HTML, PDF и DOCX) — в [`docs/manuals`](docs/manuals).
«Руководство» внизу бокового меню открывает их прямо в приложении (`#/guide`: оглавление, поиск, раздел в адресе —
HTML из `docs/manuals/*.html`, иллюстрации по `/manuals/images/…`), «О программе» — ещё и PDF и DOCX
(`/manuals/user-guide.pdf`, `?download=1` — скачать; руководство администратора — только администратору).

**Версии.** История версий для пользователей — [`docs/versions.md`](docs/versions.md) («## Версия X.Y.Z (дата)»,
описание, разделы «### …» со списками). Первая запись — текущая версия: её показывает приложение и подставляет
сборка руководств. Новую версию начинают с новой записи в этом файле.
Источники — Markdown рядом с ними. Пересборка после изменений интерфейса (нужны pandoc 3, LibreOffice,
python-docx, pypdf и Playwright с Chromium):

```bash
pip install -r requirements-dev.txt python-docx pillow
python tools/docs/shots.py           # скриншоты на демо-стенде (временная БД и учебная Jira)
python tools/docs/build_manuals.py   # HTML для чтения в приложении, PDF и DOCX
```

## Быстрый запуск (временный, без systemd/Nginx)

Для временного запуска на сервере без настройки systemd и Nginx — одной командой через gunicorn:

```bash
cd /opt/burndown
source venv/bin/activate
python init_db.py

gunicorn app:app --bind 0.0.0.0:39661
```

Приложение будет доступно по адресу `http://<IP-сервера>:39661`.

Опциональные параметры:

```bash
# С указанием ключа и путей к БД
gunicorn app:app --bind 0.0.0.0:39661 \
  --env SECRET_KEY=$(openssl rand -hex 32) \
  --env DB_PATH=/opt/burndown/burndown.db

# С 4 воркерами для боевой нагрузки
gunicorn app:app --bind 0.0.0.0:39661 -w 4

# С логированием в файл
gunicorn app:app --bind 0.0.0.0:39661 --access-logfile - --error-logfile -
```

Остановка — `Ctrl+C` в терминале. Для постоянной работы используйте systemd (раздел 6 выше) или `nohup`:

```bash
nohup gunicorn app:app --bind 0.0.0.0:39661 > /tmp/burndown.log 2>&1 &
```

cd burndown-app

## Автотесты

```bash
pip install -r requirements-dev.txt
playwright install chromium   # браузер для e2e-тестов (один раз)
pytest                        # все тесты
pytest tests/test_api.py tests/test_pdf.py   # только API и PDF, без браузера
python -m coverage run -m pytest && python -m coverage report   # покрытие кода тестами
```

- `tests/test_api.py` — API: авторизация, права доступа, CRUD, валидация, реестр изменений.
- `tests/test_pdf.py` — PDF-выгрузка: итоги, burn rate, фильтры, вспомогательные функции.
- `tests/test_e2e.py` — интерфейс в браузере (Playwright): расчёты на дашборде и своде, сортировка,
  режим просмотра, модальные окна, профиль, администрирование, мобильная вёрстка.
  Если браузер не установлен, тесты пропускаются; путь к уже установленному Chromium
  можно задать переменной `CHROMIUM_PATH`.
- `tests/test_forecast.py` — серверный прогноз совпадает с прогнозом интерфейса (сверка с `static/js/app.js` через Node.js).
- `tests/test_analytics.py` — корректность аналитики в редких случаях: ровный и обнулившийся остаток, этапы с разными датами замеров, дайджест и PDF.
- `tests/test_robustness.py` — отказоустойчивость: сбои Jira, почты, Telegram и планировщика, отказ в доступе.
- `tests/test_insights.py` — «Выводы» на уровнях эпика, этапа, проекта и портфеля, личный вид, выводы в дайджесте и PDF, единицы и рабочие дни.
- `tests/test_onboarding.py` — мастер подключения проекта, эпики, цели и «Сдано» из Jira, синхронизация перед автозаполнением.
- `tests/test_system.py` — производственный календарь (247 рабочих дней в 2025–2027), «Состояние системы», оповещения администратору.
- `tests/test_structure_columns.py` — показатели из колонок Structure (поле, сумма по вложенным, формула) через Value API.
- `tests/test_jira.py`, `test_autofill.py`, `test_history.py`, `test_composition.py` — связь с Jira (поддельный сервер Jira), автозаполнение, восстановление истории, состав задач.
- `tests/test_notifications.py`, `test_hardening.py`, `test_about.py` — уведомления, защита, «О программе» и руководства.

Тесты автоматически запускаются в GitHub Actions на каждый push и pull request (`.github/workflows/tests.yml`);
сборка падает, если покрытие серверного кода тестами ниже порога из `.coveragerc` (95 %).

Тесты используют временную копию демо-базы из `init_db.py` и не затрагивают рабочую `burndown.db`.
